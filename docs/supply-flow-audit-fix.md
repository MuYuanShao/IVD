# 进销存与结算闭环审计修复

## 已确认的结算规则

| 采购结算模式 | 自动触发时机 | 结算类型 |
|---|---|---|
| 消耗结算 | 科室实际消耗并写入 CONSUME 流水 | CONSUMPTION |
| 领用结算 | 科室签收实际配送流水 | REQUISITION |
| 调拨结算 | 科室签收实际配送流水 | TRANSFER |
| 验收结算 | 采购验收入库并写入 INBOUND 流水 | INBOUND |

同一采购来源、同一份数量只按一种模式收费。签收模式和验收模式的库存后续消耗不再生成消耗费用。未知历史来源／模式不自动推断，不对原有7条未匹配消耗记录自动补账；人工结算也不能绕过来源模式校验。

## 修复内容

- 验收必须维护批号、未过期有效期、正数数量及非负来源单价。先校验再更新收货量；订单取消／完成不能继续验收，不能出现“验收完成但未入库”。无采购单直收也复用同一验收逻辑。
- 普通检验技师、科主任可以创建／提交本部门申领和签收；科室、目标库房及机构在服务端再次核对，拣选来自中心库。
- 库存保留采购明细来源、单价及结算模式，按 `inventory_generation` 区分库存生命周期。同批号不同采购来源不混账；耗尽旧记录保持 CONSUMED，新补货创建新ID，不复活终态，也不更改旧追溯ID。
- 发货和签收优先采用真实 batch_id。缺少库存ID且存在多来源的历史流水拒绝猜测，要求人工核对。
- 消耗／验收与自动结算采用同步事务事件，财务或业务事件保存失败时连同库存、流水及状态一起回滚；每个来源流水有唯一结算防重。
- 批量签收入口不共享整批事务，逐单 REQUIRES_NEW，单据失败不会回滚其他成功单。
- 冲销必须给出原因，锁定有效结算后，同事务写入不可变 `settlement_event`；不自动返库存。创建事件与冲销事件都可从前端“追溯”查看。
- 消耗与结算不再直接注入其他模块 Mapper，通过 Service／共享事件契约协作；没有引入反向 Maven 依赖。
- 签收入库后的唯一码恢复在库状态，可供核销；唯一码管控数量必须为完整单位且核销数量一致。
- 结算单号保留既有 REQ／TRF／CNS 前缀；仅新验收类型使用 INB。未修改标本号、患者号或任何已有业务单号。

## 前端

- 验收表提示批号／有效期必填，消费批次选择展示真实库存ID及模式，避免同批号多来源误选。
- 消耗记录展示来源ID、结算模式、真实消耗结算单号及冲销状态；来源未知明确“历史待核对”。
- 来源ID按文本输入并校验 BIGINT 范围，避免 Snowflake ID 经 JavaScript Number 舍入。
- 月结算金额改为真实数据，金额缺失不展示虚构数值。财务、库管首页按机构汇总，不强行要求科室；普通科室用户仍按科室约束。
- 新追溯弹窗复用 Element Plus 与既有视觉规范，保留原页面布局。
